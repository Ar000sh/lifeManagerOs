# Phase B — Bot Integration & Cutover (Design)

**Date:** 2026-07-01
**Branch:** `feat/dynamic-skills`
**Supersedes:** the thin "Integration / skills" sketch at the end of
`docs/superpowers/specs/2026-06-27-lifeos-mcp-server-design.md`.
**Depends on:** Phase A (lifeos MCP server, 98 tests green) and the schema specs
`lifeos-mcp/docs/superpowers/specs/2026-06-29-dynamic-task-schema-design.md` and
`…/2026-07-01-key-dates-as-reminders-design.md`.

## Goal

Wire the standalone `lifeos` MCP server into the Telegram bot and cut the daily skills
(`/today`, `/week`, `/add`) over to it, so the agent calls deterministic tools instead of
resolving Notion itself. After this, swapping the map (not the code) reconfigures the
workspace, and the schema/key-date behavior built in Phase A is what actually runs.

## Readiness assessment (as of 2026-07-01)

**Phase A is code-complete and green, but Phase B is NOT ready to flip on.** Blockers:

| # | Severity | Gap |
|---|----------|-----|
| 1 | 🔴 blocker | The real `context/lifeos.map.json` is **old-shape**; the server needs **new-shape**. |
| 2 | 🔴 blocker | `/refresh-notion` still emits old-shape; can't regenerate a usable map. |
| 3 | 🟠 | `/today` `/week` `/add` skills still resolve Notion themselves; must thin onto tools. |
| 4 | 🟠 | lifeos must be registered **programmatically** (project `.mcp.json` is skipped headless). |
| 5 | 🟡 | `lifeos_mcp` + deps importable in the bot runtime; **map persistence** moves to identity-keyed Azure Blob (new infra + app store). |

## Current architecture (as-is)

```
Telegram (bot.py)
  -> agent_runner.run_agent() / LiveAgentClient
       -> Claude Agent SDK (ClaudeAgentOptions)
            mcp_servers (programmatic): notion-api (@notionhq), google-calendar (@cocal)
            setting_sources=[user, project, local]  -> loads CLAUDE.md + .claude/commands/*
            allowed_tools: Read/Glob/Grep, mcp__notion-api, mcp__google-calendar
       -> skill markdown (.claude/commands/today.md, week.md, add.md, refresh-notion.md)
            resolves Notion ITSELF via context/resolver.md + OLD map vocabulary
            (db_role_schemas, task_roles, status_values, resolved.businesses)
```

The lifeos MCP server (`lifeos-mcp/lifeos_mcp/server.py`, FastMCP "lifeos", 5 tools) is
**not referenced anywhere in the bot path.**

## Target architecture (to-be)

```
Telegram (bot.py)
  -> agent_runner -> Claude Agent SDK
       mcp_servers (programmatic): + lifeos (python -m lifeos_mcp.server, stdio)
       allowed_tools: + mcp__lifeos
  -> thin skills call lifeos tools and FORMAT the JSON:
       /today -> mcp__lifeos__get_today
       /week  -> mcp__lifeos__get_week
       /add   -> mcp__lifeos__add_record (+ create_event for calendar)
       /refresh-notion -> still the interactive map builder, emits NEW shape
  -> lifeos server talks to Notion (HttpxNotionClient) + Google (GoogleCalendarClient)
     directly, reads/writes context/lifeos.map.json (new shape, self-healing resolved cache)
```

The skills stop resolving Notion; `context/resolver.md` is retired (or kept as an internal
note). Notion IDs and column names live only in the map.

## Gap 1 (blocker) — Map schema migration

The live `context/lifeos.map.json` top-level keys today are
`workspace_root, anchors, rules, task_roles, db_role_schemas, resolved` and use
`status_values`, `resolved.businesses`, `exam_date`. The server expects
`areas`, `role_schemas` (core block + typed `fields`), `child_schema_defaults`,
`resolved.groups`, `done_predicate`/`week_predicate`. Pointing the server at the current
map yields **empty briefings** (`iter_areas` finds no `areas`, `schema_for` finds no
`role_schemas`).

**Approach: regenerate, don't hand-edit.** Per the dynamic-schema spec, the map is
regenerated by the upgraded `/refresh-notion` (Gap 2) with introspected types and the new
shape. No one-off migrator and no manual editing — `/refresh-notion` is the single source
of truth for the map.

## Gap 2 (blocker) — Rewrite `/refresh-notion` to the new shape

Rewrite `.claude/commands/refresh-notion.md` so bootstrap/sync produce the new schema:

- Discover **areas** (life areas: university, work, ventures, …), each with `sources`
  (anchored DBs), optional `group` (child-enumerated ventures), and optional `catalog`.
- For each source, write a `role_schemas[...]` entry with the **core block**
  (`title`, `due_date`/`date`+`start`+`end`, `done_predicate`, optional `week_predicate`)
  plus a typed **`fields`** table. **Introspect** Notion property names + types to seed each
  field's `type` (the supported set: title, date, select, status, checkbox, number,
  relation, rich_text, multi_select, people, url, email, phone_number).
- `done_predicate` unifies both done-rules: status-value
  (`{col, type: status, equals: "Done"}`) and checkbox (`{col, type: checkbox, equals: true}`).
- Group children keyed by Notion **page id** in `resolved.groups`; non-venture pages in
  `resolved.ignored`; `child_schema_defaults` for discovered ventures.
- **Key-date lifecycle:** a newly discovered date column is registered in `fields` as
  `{type: date, highlight: false}`; ask **once** whether to make it a key date; store the
  decision; never re-ask. (Key dates render as exact-day reminders — see the key-dates spec.)
- **Drift:** new non-date column → add to `fields` (no prompt); a schema-referenced column
  vanishing → warn + tombstone; a type change in Notion → update the map's type and warn.
- Regenerate `context/notion.md` from the new-shape map.

`/refresh-notion` stays interactive and runs through the agent (the MCP server itself is
non-interactive and only reads the map).

## Gap 3 — Thin the daily skills onto the tools

Rewrite the three skills to call a tool and format the structured result. No IDs, no column
names, no resolution logic.

- **`/today`** → `mcp__lifeos__get_today`. Render per area: tasks (mark `overdue`),
  the **"Key dates"** reminders section (Format 1: `• {label} — {title}`, rendered **only**
  in that section — do **not** re-print highlighted dates inline among a task's fields),
  the work shift, and calendar events. If the tool returns `{"error": "reconnect_notion"}`,
  tell the user to reconnect Notion instead of printing an empty briefing. Surface
  `warnings` succinctly.
- **`/week`** → `mcp__lifeos__get_week`. Same conventions, bucketed by day; key dates appear
  on their own day (the week view is day-by-day, unlike `/today`'s exact-day rule).
- **`/add`** → `mcp__lifeos__add_record` for tasks/records, `mcp__lifeos__create_event` for
  calendar. Surface the structured outcomes: `created`, or the no-guess errors
  `ambiguous_destination` / `destination_not_found` (echo `candidates`) and
  `missing_required` (echo `fields`, e.g. a task without `due_date`). A declared field with
  an unsupported type makes the tool **raise** `UnsupportedFieldType` — treat as a map bug to
  fix in `/refresh-notion`, not a user error.
- Retire `context/resolver.md` as a consumer contract (or keep as an internal note); the
  skills no longer resolve Notion.

## Integration wiring (`telegram-bot/agent_runner.py`)

- In `build_options()`, add a **third programmatic** stdio MCP server:
  `command = python` (the bot's interpreter), `args = ["-m", "lifeos_mcp.server"]`,
  `env = {NOTION_TOKEN, GOOGLE_OAUTH_CREDENTIALS, GOOGLE_CALENDAR_MCP_TOKEN_PATH,
  LIFEOS_IDENTITY, LIFEOS_MAP_STORE, LIFEOS_BLOB_ACCOUNT_URL, LIFEOS_MAP_CONTAINER}`
  (and optionally a TZ if non-default). The token env vars already exist in the bot
  environment; the persistence vars are new (see "Map persistence" below).
- **Thread the chat id through.** `run_agent(prompt)` / `LiveAgentClient` must learn the
  Telegram **chat id** (known to `bot.py`, currently locked to `1672283963`) and pass it as
  `LIFEOS_IDENTITY` in the spawned server's env, so the server loads/saves that identity's
  map. Today that's one value; later it becomes the per-user id.
- Add `"mcp__lifeos"` to `allowed_tools`.
- **Do not rely on project `.mcp.json` for the bot** — `agent_runner.py` documents that
  project `.mcp.json` servers are silently skipped in headless SDK runs. A `.mcp.json` entry
  is still worth adding **only** so interactive Claude Code (desktop/CLI) sees the same
  tools; it has no effect on the running bot.

## Map persistence — identity-keyed Azure Blob

The map stops being a single local file and becomes **one object per identity** in durable
cloud storage, so it survives VM rebuilds and is forward-compatible with multi-user.

**Identity.** The store key is the **Telegram chat id** now (`LIFEOS_IDENTITY`), the
**user id** later — same interface, different key.

**App layer (`lifeos-mcp`).** Introduce a small `MapStore` abstraction; `config.py` /
`server.py` stop calling `load_map(path)`/`save_map(path)` directly and instead use
`store.load(identity)` / `store.save(identity, data)`:
- `FileMapStore` — local dev: `…/maps/{identity}.json` on disk (default when
  `LIFEOS_MAP_STORE != "blob"`).
- `AzureBlobMapStore` — production: blob `{identity}.json` in container
  `LIFEOS_MAP_CONTAINER` of account `LIFEOS_BLOB_ACCOUNT_URL`. Auth via
  `azure-identity` `DefaultAzureCredential` → the VM's **system-assigned managed identity**
  (no secrets in env or Key Vault). New deps: `azure-identity`, `azure-storage-blob`.
- Selected by `LIFEOS_MAP_STORE = file | blob`.
- *Concurrency note:* read-modify-write per tool call (the `resolved` cache self-heals on
  read). Single-user + sequential bot handling makes races unlikely; ETag-based optimistic
  concurrency is a future hardening, not v1.

**Infra layer (`infra/`, ships through the gated CI/CD pipeline; Claude writes the files +
commands, Aroosh approves/applies — never `terraform apply` on his behalf).** Add a new
`infra/storage.tf` with its `infra/doc/storage.tf.md` explainer (per the docs rule):
- A **new** app-data storage account in `azurerm_resource_group.main` (do **not** reuse the
  tfstate account `stlifeostf18906` — separation of concerns). Name like
  `st${var.prefix}data…` (globally unique, lowercase, ≤24 chars; mirror the random-suffix
  pattern of the tfstate account).
- An `azurerm_storage_container` "maps" (private).
- An `azurerm_role_assignment` "vm_storage": scope = the storage account, role =
  `Storage Blob Data Contributor`, principal = `azurerm_linux_virtual_machine.main.identity[0].principal_id`
  — mirroring the existing `vm_kv` / `vm_acr` least-privilege grants.
- Surface the account blob endpoint via `outputs.tf`; pass it to the bot as
  `LIFEOS_BLOB_ACCOUNT_URL` (+ `LIFEOS_MAP_CONTAINER`, `LIFEOS_MAP_STORE=blob`) through
  `cloud-init.yaml.tftpl` / the bot env (the URL is not a secret).

## Gap 5 — Runtime dependencies

- The bot process must be able to `import lifeos_mcp` and its deps (`mcp`/FastMCP, `httpx`,
  the Google client libs used by `calendar_client.py`, and now `azure-identity` /
  `azure-storage-blob`). Install the package into the bot's runtime:
  `pip install -e ../lifeos-mcp` (or add it to `telegram-bot/requirements.txt`), and pin
  `lifeos-mcp`'s own deps there too.
- No Docker volume for the map is needed — persistence is Azure Blob (above). The container
  just needs the package + deps installed.

## Decisions (locked 2026-07-01)

1. **Calendar + Notion overlap — LOCKED (2026-07-01): keep both npx servers alongside lifeos.**
   The `@cocal/google-calendar` and `@notionhq/notion-api` npx servers stay registered for
   ad-hoc ops the 5 tools don't cover. The **daily skills use lifeos**; ad-hoc requests may use
   the npx servers. Calendar shares one cached OAuth token path (no double auth). Mitigate the
   agent mixing paths via skill wording ("for /today /week /add use the lifeos tools").
2. **`/add` event creation — LOCKED (2026-07-01): lifeos `create_event`** for the common case;
   the Google MCP remains available for anything richer.

## Out of scope

- Full multi-user onboarding (auth, per-user provisioning). The **storage is already
  identity-keyed** (chat id → user id), so going multi-user is a key change + onboarding,
  not a storage rebuild.
- The template layer (authoring record types, required custom fields).
- Mutations beyond create (`update_record`, `mark_done`, calendar move/delete).
- Structure creation (new businesses/DBs/sections/views).
